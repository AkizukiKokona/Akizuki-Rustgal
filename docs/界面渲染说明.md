# 界面渲染说明

本文档说明 `akrs-render` 中几处与用户可见界面相关的渲染规则，便于后续维护时快速定位行为。

## 存档/读档页缩略图

存档页与读档页的每个槽位左侧有一个 16:9 缩略图，由 `draw_slot_thumbnail` 绘制。
渲染规则按优先级如下：

1. **有场景快照**（`SaveSlot.scene` 存在）：按比例缩小重绘存档时的背景与立绘，
   即"读档后看到的画面"的缩略版。背景采用 cover 模式（填满 16:9 缩略图区域，
   超出部分裁剪，与主场景 `draw_background` 一致）；立绘按缩略图高度等比缩小，
   超出缩略图区域的部分同样裁剪，避免突出到边框外污染相邻格子（详见下文
   「缩略图裁剪」）。
2. **存档存在但无场景快照**（理论上不再发生，见下文「旧格式存档升级」）：
   用标题图 `assets/title.png` 作兜底画面。这是防御性回退，正常情况下旧存档
   在启动时已被升级补上 `scene` 字段。
3. **标题图也加载失败**（极少见）：绘制深色底占位，避免空白。
4. **空槽位**（无存档）：由调用方绘制翻译后的"空"字样（`save.empty`），不进入
   `draw_slot_thumbnail`。

> 设计意图：所有有存档的槽位都必须出画面，不能仅以文字代替。场景快照由
> `Engine::scene_snapshot` 在存档时写入，包含背景、立绘、音乐三类持久态。

## 缩略图裁剪（cover 模式 + draw_texture_clipped）

缩略图区域固定为 16:9 矩形 `(x, y, w, h)`。背景用 cover 模式（填满区域，
超出部分裁掉），立绘按位置定位也可能超出区域。为保证缩略图"和用户看到的
一样"且不突出到边框外污染相邻格子，所有绘制都用 `draw_texture_clipped`
裁剪到该矩形内。

### 实现原理

macroquad 0.3 的 `DrawTextureParams.source` 接受源纹理像素坐标的 `Rect`，
表示只绘制源纹理的这一部分。`draw_texture_clipped` 计算**目标绘制矩形**
`(dx, dy, dw, dh)` 与**裁剪矩形** `(x, y, w, h)` 的交集，把交集映射回源
纹理坐标，用 `source` 只绘制可见部分，`dest_size` 设为交集大小：

- 交集为空（无重叠）则跳过绘制。
- 交集映射：交集在目标矩形内的偏移比例 `(u, v)` 乘以源纹理尺寸，得到
  `source` 的像素坐标。
- 这样背景 cover 模式左右/上下超出部分、立绘超出底部的部分都不会画到
  缩略图矩形外。

### 与主场景的一致性

- 背景：`s = (w/tex_w).max(h/tex_h)`（cover），与 `draw_background` 相同。
- 立绘：`y_frac=1.0` 时贴齐缩略图底部（`h - dh - 50×(h/1080)`），与
  `draw_characters` 的底部对齐一致；否则中心点对齐 `y_frac`。
- offset/scale/alpha 均按缩略图尺寸等比换算。

## 旧格式存档升级（场景重建）

旧格式存档没有 `scene` 字段，读档后会背景黑屏、立绘消失，缩略图也会回退到
标题图。为此引擎提供「场景重建」机制：

### 重建原理

`Vm::rebuild_scene_to(target_section, target_ip)` 从入口 section / ip 0 开始
重放指令，直到到达存档点 `(target_section, target_ip)`，收集沿途的
`@bg` / `+角色` / `@music` 等**持久态指令**事件：

- `Command` / `Direction`：正常执行并收集（设置背景/立绘/音乐）。
- `VarOp` / `Jump` / `JumpIfFalse` / `SectionJump` / `VisitCall` / `Return`：
  正常执行（影响控制流），不收集。
- `Dialogue` / `Narration` / `Wait`：重建模式下视为"已播放过"，只推进 ip，
  不产生事件。
- `Choice`：按已保存的变量评估各选项条件，取第一个 available 选项跳转
  （模拟玩家当时的选择）。
- 设置 100000 步上限防止死循环；到达目标点或越界则停止，返回已收集的事件
  （部分重建好过完全不重建）。

`Engine::rebuild_scene_for_slot(slot)` 用重建事件**直接应用到临时 scene**
（绕过过渡，只关心最终态），构造 `SceneSnapshot` 返回。重建前后用
`save_state` / `load_state` 保护当前 VM 状态，不影响游戏进度。

### 升级时机

1. **启动时一次性升级**：`run()` 启动时调用 `engine.upgrade_all_legacy_saves()`，
   扫描所有常规槽位（0..max_slots），对无 `scene` 的存档重建并回写
   （`SaveManager::upgrade_scene`）。这样存档页缩略图能直接用 `scene` 字段
   渲染真实画面，读档也不再黑屏。
2. **读档时按需升级**：`Engine::load` 读档时若存档仍无 `scene`（例如启动升级
   失败或新增的旧存档），再次重建并回写，确保读档后场景正确恢复。

autosave / continue / quicksave 在各自读档路径中按需重建升级，不参与启动扫描。

## 存档页布局（1.2x 放大）

存档/读档页在 dpi 适配系数 `scale` 之上叠加 `SAVE_ZOOM = 1.2` 放大倍率，
让存档格子更饱满：

- `eff = scale * 1.2`（有效倍率 = dpi × 存档页放大）。
- `cell_h = 240 × eff`、`gap = 29 × eff`：高度与间距按 1.2x 放大。
- `cell_w`：按 4 列不溢出屏幕宽度反算（`usable_w = sw - 2×24×scale`），
  同时不超过基准 `408 × eff`，避免超宽屏上格子过宽破坏比例。
- `draw_slot_cell` 与 `draw_page_nav` 接收 `eff` 作为 scale，内部所有元素
  （缩略图、文字、按钮）自动 1.2x 放大。
- 返回按钮保持标准 `scale`（dpi 适配），作为通用控件不参与存档页放大。
- `grid_y = sh × 0.22`：网格起始位置略上移，为放大后的格子腾出垂直空间。

多 dpi 适配保留：`scale` 仍由屏幕 dpi 决定，`SAVE_ZOOM` 仅作用于存档页。
例如 150% dpi 下 `scale ≈ 1.5`，存档页有效倍率 `eff ≈ 1.8`。

## 存档格子文本截断处理

存档格子右侧文字栏（章节名 / 描述 / 备注）在空间不足时会截断，并按以下规则
提供 hover tooltip 显示完整内容：

- **章节名**：`fit_text` 单行截断。截断时（`section_display.ends_with('…')`）
  标记 `section_truncated`。
- **描述**：`wrap_text_cn` 按可用高度动态计算行数（`desc_max_lines`，放大后
  区域变大可显示更多行），末行省略。通过对比"不限制行数时的总行数"与
  "限制后的行数"判断是否截断（`desc_truncated`）。
- **备注**：`fit_text` 单行截断。截断时标记 `note_truncated`。
- **Tooltip 触发**：hover 时若任一文字被截断，组合完整信息
  （章节名 / 描述 / 📝备注，缺省项跳过）用 `\n` 连接，通过 `draw_tooltip`
  显示在鼠标附近。tooltip 在所有元素之上最后绘制。

## 关于页头像

设置页「关于」选项卡左侧显示头像，头像图片为项目根目录的 `kokona.png`。

- 加载路径：`../kokona.png`，相对于资源基目录 `assets/` 解析为项目根目录的
  `kokona.png`（即 `assets/../kokona.png`）。
- 加载在 `run()` 启动时一次性完成并缓存，关于页每帧复用该纹理。
- 加载失败时绘制占位线框。
- 头像按 contain 模式缩放到与 3 行文字等高的正方形区域内。

## 过渡合并（立绘叠叠乐修复）

### 问题：过渡进行中指令丢失

过渡系统用两阶段状态机（Out → Swap → In）：`start` 时把待应用的场景变更
存入 `pending`，Out 阶段结束（swap point）才真正应用到现场 `scene`。Out
阶段进行中，现场 `scene` 仍是**过渡前的旧状态**，而 VM 已经越过触发过渡的
指令继续执行下一条。

若此时又遇到 `+角色` / `-角色` / `@bg` 等指令，**不能直接修改现场 scene**：

- `-角色`（exit）：现场是旧状态，该角色可能尚未入场，`character_exit` 变成
  no-op，exit 指令丢失 → 本该下场的立绘残留在屏幕上"下不去"（叠叠乐）。
- `+角色`（enter）：现场被改了，但 swap point 会用旧 pending 覆盖现场，
  enter 也可能丢失。
- `@bg`：直接改现场会被 swap point 的旧 pending 覆盖，bg 指令丢失。

### 解决：merge_into_pending

`TransitionManager::merge_into_pending` 在过渡 active 时把后续指令**合并到
当前 pending**，等 swap point 一次性按顺序应用所有累积变更。`Engine` 的
`handle_direction`（Enter/Exit）和 `handle_command`（bg）在
`self.transition.is_active()` 为真时调用 `merge_into_pending`，否则照常
`start` 一个新过渡。

### 合并语义

- `chars_exit`：追加到 pending 的 exit 列表（去重，避免同一角色被多次 exit）。
- `chars_enter`：追加到 pending 的 enter 列表；若同名角色已在 enter 列表中则
  替换其条目（与 `character_enter` 的 replace 语义一致）。若同名角色同时在
  exit 列表中，先从 exit 移除（入场应覆盖之前的下场意图）。
- `new_bg` / `new_music`：后指令覆盖 pending 中已有的值。

### 与存档快照的配合

存档构造快照时，`apply_pending_to` 把 pending 应用到快照副本（不动现场），
让快照与 VM 指针保持一致——避免读档后 pending 变更永远不会被执行（VM 不会
再重放那条指令）。`merge_into_pending` 保证 pending 累积了过渡期间所有指令，
所以快照能正确反映过渡结束后的最终态。

### 边缘情况

同过渡内对同一角色先 enter 再 exit：merge 后 enter 列表与 exit 列表都含该
角色，`apply_changes` 先 exit（no-op，角色不存在）后 enter，结果是角色入场
（enter 胜出）。这是边缘情况（同过渡内 enter 又 exit 同一角色），实际剧本
罕见，当前行为可接受。反向（先 exit 再 enter）按 merge 语义 enter 时从 exit
移除，最终 enter 胜出，角色在场。

## Build 号与版本号显示

关于页第 3 行显示版本与 Build 号，格式为 `版本 1.0(Build 0043)`。

### 版本号来源

- 项目版本号定义在根 `Cargo.toml` 的 `[workspace.package] version`，遵循 SemVer，
  当前为 `1.0.43`（主版本.次版本.Build号）。
- 关于页通过 `env!("CARGO_PKG_VERSION")` 读取该值，按最后一个 `.` 拆分：
  前两段作为主次版本（如 `1.0`），最后一段作为 Build 号数字（如 `43`）。
- 显示时 Build 号按四位数补零（如 `43` → `0043`），格式为 `版本 1.0(Build 0043)`。
- README.md 顶部的 version badge 同步使用该版本号。
- 注：SemVer 不允许 patch 段有前导零，故 Cargo.toml 写 `1.0.43` 而非 `1.0.0043`，
  显示时再补零。

### Build 号生成规则

`crates/akrs-render/build.rs` 在编译时执行：

```text
BUILD_NUMBER = git rev-list --count HEAD + BUILD_BASE
```

- `git rev-list --count HEAD`：当前分支的 commit 数。
- `BUILD_BASE = 37`：基数。本仓库 main 分支 git 历史曾做过压缩/重置，commit 数
  从 1 重新计数，叠加基数 37 后与项目实际迭代进度（含历史提交）对齐。
- 例：commit 数为 6 时，BUILD_NUMBER = 6 + 37 = 43，显示 `Build 0043`。
- 后续每次提交 commit 数 +1，Build 号同步 +1，无需手动调整。

### 版本号与 Build 号的关系

`Cargo.toml` 版本号的 patch 段应与 `BUILD_NUMBER` 保持一致。每次提交后：

1. `build.rs` 自动算出新 BUILD_NUMBER（commit 数 + 37）。
2. 手动把 `Cargo.toml` 的 `version` patch 段更新为该数字（不补零，SemVer 要求）。
3. README badge 同步更新。
4. 关于页显示时会自动补零为四位数。

这样关于页从 `CARGO_PKG_VERSION` 读取的值与 `BUILD_NUMBER` 始终一致。
